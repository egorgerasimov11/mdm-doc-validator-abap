# Правила: как смотреть, менять, удалять и заменять («скиллы»)

> English version: [RULES.md](RULES.md)

Правила решают вердикт (модель ничего не решает). Каждый **тип документа — отдельный набор-«скилл»**,
который можно заменить целиком: `banking` (валидация банковского документа) и `w9` (проверка W-9).

## Где они хранятся (3 слоя, не зашиты намертво)

1. **Источник** — YAML: [`rules/banking.yaml`](../rules/banking.yaml), [`rules/w9.yaml`](../rules/w9.yaml).
   Человекочитаемо, тут удобнее всего править насовсем.
2. **Скомпилированный ABAP** — `ZCL_MDMDOC_RULES_DATA` (генерируется из YAML, исполняется в SAP).
   Руками не трогают.
3. **Runtime-override JSON** — `rules/rules.json` (весь набор), `rules/banking.rules.json`,
   `rules/w9.rules.json` (пер-класс «скиллы»). Грузятся параметром `p_rules` отчёта `ZMDMDOC`
   на лету, **без перегенерации и транспорта**.

## Посмотреть правила в SAP

Отчёт **`ZMDMDOC_RULES`** (SA38): показывает все правила (id, серьёзность → вердикт, к каким типам
применяется, условие человекочитаемо, текст EN/RU; цвет по серьёзности). Радио `Все / Banking / W-9`.

## Структура одного правила

```json
{
  "id": "W9-010",
  "name": "ein_9_digits",
  "applies_to": ["w9"],                 // пусто = ко всем типам
  "when_op": "check",                   // always | field_missing | flag_true/false | equals | in | regex_mismatch | check
  "when_field": "tin_raw",
  "check_name": "ein_shape",            // для when_op=check — какой предикат
  "check_args": [{ "name": "digits", "value": "9" }],
  "severity": "CRITICAL",               // CRITICAL | WARNING | NOTE
  "verdict_effect": "NEED_MANUAL_REVIEW", // REJECT | NEED_MANUAL_REVIEW | WARNING | "" (без эффекта)
  "message": "TIN {value} has the wrong digit count ...",
  "message_ru": "…",                    // опционально
  "tier": "corp"                        // governance: corp | experimental | learned
}
```

## Governance-профиль (tier)

Каждое правило несёт метку `tier`. Дефолтная генерация шипит **полный набор** (включая
experimental `BNK-002` — email-как-подтверждение REJECT, и `BNK-030` — нераспознанный
документ → NEED_MANUAL_REVIEW, безопасный страховочный). Строгий corp-профиль:
`python3 tools/gen_rules_abap.py --tier-min corp` — experimental-правила исключаются.
Правила без tier проходят фильтр всегда.

## Особые правила, о которых надо знать

- **`W9-030`**: любой документ, распознанный как **W-8** (W-8BEN/-E), безусловно уходит в
  `NEED_MANUAL_REVIEW` — W-8 compliance-политика сознательно не автоматизирована в v1.
- **`BNK-030`** (experimental): документ, тип которого не удалось установить, никогда не
  проходит автоматически — `NEED_MANUAL_REVIEW`.
- **Ошибка движка = fail-closed**: правило, упавшее при вычислении (или с невалидным
  `verdict_effect`), даёт finding `ENGINE-GUARD` с эффектом `NEED_MANUAL_REVIEW` —
  сломанное правило не может привести к молчаливому ACCEPT.

## Способ 1 — на лету, без транспорта (проще всего)

1. `ZMDMDOC_RULES` → флажок «Export» → путь файла (можно выбрать один класс: `W-9 only` →
   выгрузит только `w9.rules.json`).
2. Открыть файл, поправить:
   - **изменить** правило — поменять его поля (severity, message, verdict_effect…);
   - **удалить** правило — убрать его блок `{ ... }` из массива;
   - **добавить** — вписать новый блок с уникальным `id`;
   - **заменить весь «скилл»** (например W-9) — взять файл `w9.rules.json` целиком и подложить свой.
3. Запустить `ZMDMDOC`, в блоке Output указать этот файл в параметре **rules override** (`p_rules`).
   Правила применятся из файла. Битый JSON → предупреждение + откат на вшитые правила.

**Пер-класс «скилл»-swap:** файл с только `rules_w9` заменяет **лишь** W-9, банковский модуль
остаётся дефолтным (и наоборот). То есть «что-то не так с W-9 → подменил `w9.rules.json`», не задев
банковский.

## Способ 2 — насовсем, через источник

1. Править `rules/banking.yaml` / `rules/w9.yaml` (тот же смысл полей, но в YAML).
   Удалить правило = убрать его пункт из списка `rules:`.
2. `python3 tools/gen_rules_abap.py` — перегенерирует `ZCL_MDMDOC_RULES_DATA` + все `*.rules.json`
   (нужен Python 3 + PyYAML; это единственная Python-зависимость репозитория).
3. abapGit Pull в систему → активировать → (при переносе) транспорт.

## Способы 3–4 — только на стороне автора (Python-репозиторий)

Веб-панель Python-оригинала (`mdmdoc ui`) и синхронизация из checker-скиллов
(`mdmdoc skill-rules`, процедура `mdmdoc-skill-sync`) живут в родительском Python-проекте
и **недоступны на целевой SAP-системе** — упомянуты для полноты картины: именно там
рождаются и проходят human-approval новые правила, которые затем приезжают сюда
Способом 2.

## Важно

- Низкоуровневые проверки (IBAN mod-97, `ein_shape`, `swift_valid`…) — это скомпилированные
  «кирпичи» ABAP, общие для всех; их не меняют через файл. Меняют **набор правил** (какие проверки
  применять, серьёзность, тексты) — а он заменяем.
- После правки: `ZMDMDOC_RULES` покажет, что реально активно; тест `describe_conditions` +
  `skill_swap_partial` в юнит-тестах фиксируют формат и пер-класс поведение.
